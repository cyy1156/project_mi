## 4. 两方案利弊对比

### 方案甲：现在重构（推荐，分轨执行）

**利：**
1. **正处修订窗口**——20 人战役 D1–D3 本来就是"调试队列、协议修订窗口"，现在不修，开战后没有窗口
2. **P0 隐患在战役期间爆发的代价最高**：23 名被试 × 60–75 分钟/人，一次 fnz_ws07 式断流或 eeg.meta 缺失 = 一场白采；收尾兜底协议（W2 遗留）直接决定数据完整率
3. **A/B 轨零规则风险**：解反向依赖只改 import 行，不改任何实验语义；冻结文档明文"配置+代码为权威源"
4. **代码质量债不随时间缩小**：orchestrator 114KB、7 处反向依赖会随每次新功能加深，战役后改的成本只增不减

**弊：**
1. 约需 2–4 个工作日工程投入，占用采集准备时间
2. 无基线提交的情况下动手有回归风险（必须先做第 5 节第 0 步）
3. 短期内"能跑"的代码被改动，需要合成板冒烟验证

### 方案乙：等规则全部冻结（含 F5）再改

**利：**
1. 短期零回归风险，人力全部投向采集准备
2. 一次改到位，避免返工

**弊：**
1. **F5 是循环依赖的死锁**：F5 需要"更多被试的矛盾率数据"才能定 → 需要跑 20 人战役 → 战役又需要 P0 修复和收尾兜底保数据 → 你在等一个"必须先重构才能解锁"的规则
2. 战役开打后无修订窗口，任何 bug 只能带病采集或中途叫停（更贵）
3. "一次改到位"是幻觉：F5 只是计分口径，A/B/C 轨的债务与它毫无交集，等它冻结并不会让重构变得更容易
