## 2. 四大结构病

### 病 ①：业务逻辑写错层（tools 既是入口又是实现）

`tools/ft_subject_from_v3.py` 43KB，包含数据集构建（`build_dataset`）、切窗（`_build_session_windows_legacy/_build_session_windows_openbmi_align`/`_cut_windows`）、训练循环（`finetune_head`）、门控（`evaluate_release_gate`）全套业务。它是被 `orchestrator`（核心层）import 的库，又是 CLI 入口，还是 4 个 `_diag_*`/`_analyze_*` 脚本的 import 源——三种身份纠缠。
**后果**：experiment→tools 反向依赖；FT 逻辑无法被单测隔离；上一轮审查发现的"先覆盖权重再门控"P0 问题就藏在这里。

### 病 ②：共享概念没有共享层

`channel_layout`（通道序，fnz 诊断证明它是数据正确性的命门）、`class_labels`（{0,1,2} 标签）、采样率/窗长/hop 常量——这些被 offline、acquisition、experiment、tools 四方共用的概念，全部住在 experiment 包里。offline/acquisition 为了拿一个通道序定义，被迫反向依赖核心层。
**后果**：3 处反向依赖；`LABEL_*` 三处独立定义、`FS=250/N_TIMES=750` 魔法数字散落（上一轮审查 O5/L6/L7）。

### 病 ③：orchestrator 上帝对象 + 双向成环

114KB，一个文件承担 HTTP 服务、WS 消息路由（17 分支 if-elif）、会话编排、acquisition 接线、FT 调度、sim campaign、phase4 触发。它同时是 experiment→tools、experiment→offline 两条反向依赖的**唯一来源**——把 orchestrator 拆开，两个环自然解开。

### 病 ④：切窗四套并存（有逻辑错误实证）

| 管道 | 通道序 | 窗长 | 基线 |
|------|--------|------|------|
| `offline/epochs.py` | 设备序 | 2s/500 点 | 窗内前 0.5s |
| `offline/pipeline.py` | 设备序 | 2s/500 点 | 窗内前 0.5s |
| `offline/phase4_v2*.py` | 模型序 | 3s/750 点 | cue 前 0.5s |
| `offline/openbmi_align_cut.py` | 模型序 | 3s/750 点 | cue 前 0.5s |
| `tools/ft_subject_from_v3.py`（第 5 处实现） | 模型序 | 3s/750 点 | 自带一套 |

**fnz 实证**：训练侧通道序统一时 syj 能到 heldout 0.78；在线推理（inference_v2 + RingBuffer）取窗与训练切窗一致性存疑，ws07 出现 p_three 与模型偏好方向不符。这正是"没有单一真相源"的代价——不是代码写得差，是**同一个科学定义存在 5 份实现**。

## 4. 目标分层架构

```
┌──────────────────────────────────────────────────────┐
│ L6 tools/ 入口层   薄 CLI：argparse + 调用，零业务逻辑    │
├──────────────────────────────────────────────────────┤
│ L5 orchestrator    纯调度：HTTP/WS 路由 → dispatch table│
├──────────────────────────────────────────────────────┤
│ L4 session/ 会话层  SessionRunner 基类；v2/v3/v4 只写差异 │
├──────────────────────────────────────────────────────┤
│ L3 domain/ 领域层   timing·trial_sm·alignment·inference │
├────────────────────────────┬─────────────────────────┤
│ L2 pipeline/ 流水线          │ L2 runtime/ 运行时        │
│ windowing 唯一切窗·finetune  │ ring_buffer·markers·ws   │
│ ·eval_utils·filters         │ ·events_log·acquisition  │
├────────────────────────────┴─────────────────────────┤
│ L1 core/ 共享核心（零依赖）                             │
│ channel_layout·class_labels·constants·io·logging      │
└──────────────────────────────────────────────────────┘
```

**分层规则（三条，建议用 import-linter 固化成 CI 契约）：**
1. 只准上层 import 下层，禁止反向、禁止跳层（orchestrator 不得直接 import runtime 细节，须经 domain/pipeline 接口）。
2. `core/` 零本地依赖——任何模块 import core 都合法，core 不 import 任何人。
3. `tools/` 薄壳——每个 CLI ≤80 行，只做参数解析 + 调用 + 退出码。

**各层职责边界（关键决定）：**
- `core/channel_layout.py`：`MODEL_INPUT_CHANNEL_ORDER` 与 `DEVICE_CHANNEL_LABELS` 及两者互转函数，**唯一真相源**。offline、acquisition、inference 全部从这里拿，切窗双轨制的通道维随之归一。
- `pipeline/windowing.py`：切窗协议（任务段长度、窗长、hop、基线方式、阶段白名单 acquire-only）定死在**一个**模块；epochs/pipeline/phase4_v2/ft 的第 5 套实现全部删除，改为调用它。
- `pipeline/finetune.py`：FT 业务（build_dataset/finetune_head/release_gate）从 tools 下沉至此；`tools/ft_subject_from_v3.py` 缩成 60 行壳。orchestrator 改调 `pipeline.finetune`，experiment→tools 环解开。
- `session/`：抽取 `SessionRunner` 基类（会话目录创建、meta 写入、events emit、abort 处理），session_v2/v3 只保留差异逻辑（v2 的在线反馈、v3 的块结构）。预计消除 ~40% 平行代码。
- `orchestrator`：只留 HTTP/WS 路由 + 状态广播；`_on_ws_message` 17 分支改 dispatch table；FT/phase4/sim 各自成 handler 模块。

## 5. 四步迁移路线（每步可独立提交、可回滚）

### 第 1 步：新建 core/（收益最大、风险最小，先做）

- 迁入：`channel_layout`、`class_labels`、常量（FS/WIN_SEC/HOP 等全部魔法数字）、`atomic_write_text`/`atomic_torch_save`/jsonl 读写、统一 logging。
- 旧位置留一行 `from core.xxx import *` 兼容垫片，调用方逐个切换后再删垫片。
- **立即收益**：offline→experiment、acquisition→experiment 两处反向依赖消失；LABEL/魔法数字/非原子写三类重复清零。
- 预估改动：~12 个文件的 import 行 + 新建 5 个小模块。

### 第 2 步：FT 业务下沉 pipeline/

- `tools/ft_subject_from_v3.py` → 拆 `pipeline/finetune.py`（业务）+ `tools/ft_subject_from_v3.py`（60 行壳）。
- `orchestrator.py` 的 import 改为 `pipeline.finetune`——experiment→tools 环解开。
- 顺带修上一轮 P0：权重先写 `.tmp`，门控 PASS 后 `os.replace`。
- 预估改动：1 个大文件重排 + orchestrator 1 行 import。

### 第 3 步：windowing 归一（消灭双轨制）

- 先由项目负责人**定夺唯一协议**：通道序=模型序（`MODEL_INPUT_CHANNEL_ORDER`）、窗长=3s/hop100（与底座一致）、基线=cue 前 0.5s、阶段白名单=acquire only（这三项是 fnz 诊断的建议）。
- 写 `pipeline/windowing.py` 单一实现 + **单测锁死**（给定合成 events+eeg，断言输出张量形状 (N,1,8,750) 与通道序）。
- 删除 `epochs.py`/`pipeline.py` 旧切窗路径、`ft_subject_from_v3` 内第 5 套实现，全部改调 windowing。
- **风险最高的一步**（改变训练数据语义），必须在无采集任务的窗口期做，并用 syj0828 旧数据回归对比 heldout。

### 第 4 步：orchestrator 瘦身 + session 基类

- 拆出 `operator_http.py`（HTTP/WS 路由，dispatch table）、`session_runner 基类`（v2/v3 公共）、`handlers/`（ft/phase4/sim 各一）。
- orchestrator 目标 <30KB，只剩装配与路由。
- **风险中等**：纯重构不改行为，靠现有 smoke 脚本（smoke_operator_ws 等）回归。

## 6. 防回归护栏（重构后立刻加）

1. **import-linter 契约**（`pyproject.toml` 三条规则对应第 4 节分层规则），CI 里 `lint-imports` 一票否决——反向依赖永远回不来。
2. **打包**：`pip install -e .` 后删除全部 `sys.path.insert` hack（~15 处），IDE 解析恢复正常。
3. **单测锁科学定义**：通道序、窗长、标签 {0,1,2}、acquire-only 白名单各一条金样测试——任何人改切窗协议必须显式改测试。
4. **依赖方向测试**：一条测试断言 `offline`/`acquisition`/`pipeline` 的模块不得 import `experiment`/`tools`（import-linter 的 pytest 兜底）。
5. 每步迁移配一条 smoke（第 2 步用 `smoke_sim_module`、第 4 步用 `smoke_operator_ws`）。
